01

Basics & Syntax

Every DAX formula is an expression that returns a single value or a table. It's used in three places: calculated columns, measures, and calculated tables. The first choice a student makes — column or measure — decides how a value behaves for the rest of the model. Full treatment: DAX Basics & Measures.

Calculated Column

Margin = DimProduct[ListPrice] - DimProduct[StandardCost]
  • Evaluated once per row, in row context
  • Result is stored on disk, in every row
  • Can be used as a slicer, axis, or filter
  • Grows file size — use sparingly

Measure

Total Sales = SUM(FactInternetSales[SalesAmount])
  • Evaluated on the fly, in filter context
  • Never stored — recalculated per visual
  • Responds to slicers, rows, columns, CALCULATE
  • The right default for anything you aggregate
02

Aggregation Functions

The workhorses. Plain aggregators collapse a column; iterators (the X-suffixed forms) walk row by row first, so they can compute something per row before aggregating.

SUM(column)
Adds every value in a column.
Total Sales = SUM(FactInternetSales[SalesAmount])
AVERAGE(column)
Arithmetic mean of a column — careful what it's really averaging (see Pitfall below).
Average List Price = AVERAGE(DimProduct[ListPrice])
COUNTROWS(table)
Counts rows visible in current context. On FactInternetSales this counts order LINES, not orders — see Pitfall #7.
Line Item Count = COUNTROWS(FactInternetSales)
DISTINCTCOUNT(column)
Counts unique values — the correct way to count actual orders, not line items.
Order Count = DISTINCTCOUNT(FactInternetSales[SalesOrderNumber])
MIN / MAX(column)
Smallest or largest value in the current context.
First Order Date = MIN(FactInternetSales[OrderDate])
SUMX(table, expr)
Iterator: evaluates expr per row, then sums. Needed whenever the calculation itself varies row by row.
Total Margin = SUMX(
  FactInternetSales,
  FactInternetSales[SalesAmount] - FactInternetSales[TotalProductCost]
)
03

Logical & Dynamic Measures

These build conditional logic directly into a measure, so a card or KPI can change its label — or its whole calculation — based on the numbers in view.

IF(test, then, else)
Two-way branch. Nest sparingly — past 2–3 levels, switch to SWITCH.
Sales Status = IF(
  [Total Sales] > 10000000,
  "Target Met", "Below Target"
)
SWITCH(expr, val, res, ...)
Multi-way branch. SWITCH(TRUE(), ...) lets each branch be its own condition.
Season = SWITCH(TRUE(),
  MONTH(FactInternetSales[OrderDate]) IN {12,1,2}, "Winter",
  MONTH(FactInternetSales[OrderDate]) IN {3,4,5}, "Spring",
  "Other"
)
AND / OR / NOT
Combine conditions. In practice, && and || read more cleanly than nesting AND()/OR().
Big Buyer = IF(
  [Order Count] > 5 && [Total Sales] > 500000,
  "VIP", "Standard"
)
ISBLANK / COALESCE
Guard against blanks before displaying — COALESCE returns the first non-blank argument. DimProduct[Style] is genuinely blank on many real AdventureWorksDW rows, which is exactly why this pattern exists.
Style Label = COALESCE(DimProduct[Style], "Unspecified")
04

Row Context vs. Filter Context

The concept nearly every DAX mistake traces back to. Two different "current position" mechanisms exist, and knowing which one you're in decides whether a formula belongs in a column or a measure. Full treatment, including a worked matrix-cell walkthrough: Context & Dynamic Measures.

calculated columns · iterators (X-functions)

Row Context

DAX evaluates the expression once for the "current row." DimProduct[ListPrice] - DimProduct[StandardCost] works in a calculated column because each row already knows its own ListPrice and StandardCost.

measures · visuals · slicers

Filter Context

The set of filters narrowing the data before a measure runs — a slicer on ProductLine, a row for each Class in a matrix, a page filter on Year. SUM() only sees rows that survive this filter set.

Context transition
CALCULATE is the one function that converts row context into filter context — it's what lets a measure be evaluated "as if" a filter had been applied for the current row. This is why CALCULATE sits at the center of almost every non-trivial DAX formula. (One careful sentence is all this course needs — the full topic is past this module's ceiling.)
05

CALCULATE & FILTER

CALCULATE re-evaluates an expression inside a modified filter context. Everything else in this section is really just different ways of building the filter arguments it takes. Full treatment: CALCULATE, FILTER & Modeling.

CALCULATE(expr, filter...)
Replaces existing filters on the referenced column(s) with the ones you supply.
Road Bike Sales = CALCULATE(
  [Total Sales],
  DimProduct[ProductLine] = "R"
)
FILTER(table, condition)
Returns a filtered table rather than a boolean — required inside CALCULATE for logic a simple column filter can't express.
Premium Product Sales = CALCULATE(
  [Total Sales],
  FILTER(DimProduct, DimProduct[ListPrice] > 1000)
)
ALL(table / column)
Removes filters — the standard way to compute a "% of total" that ignores the current slice.
% of All Products = DIVIDE(
  [Total Sales],
  CALCULATE([Total Sales], ALL(DimProduct))
)
ALLEXCEPT(table, col...)
Removes all filters on a table except the columns listed — narrower and often safer than ALL.
Sales by Product Line Only = CALCULATE(
  [Total Sales],
  ALLEXCEPT(DimProduct, DimProduct[ProductLine])
)
06

Time Intelligence

Requires a proper Date table — in this course, DimDate, contiguous and marked as the model's official date table, related to FactInternetSales[OrderDateKey]. Every function below leans on CALCULATE's context-shifting under the hood. Full treatment, including the "two tables, one line" exception: Time Intelligence & Aggregations.

FunctionReturnsExample
TOTALYTD Running total from the start of the calendar year to the current filter date TOTALYTD([Total Sales], DimDate[FullDateAlternateKey])
TOTALQTD Running total from the start of the current quarter TOTALQTD([Total Sales], DimDate[FullDateAlternateKey])
TOTALMTD Running total from the start of the current month TOTALMTD([Total Sales], DimDate[FullDateAlternateKey])
SAMEPERIODLASTYEAR Shifts the current date filter back exactly one year CALCULATE([Total Sales], SAMEPERIODLASTYEAR(DimDate[FullDateAlternateKey]))
DATEADD Shifts the date filter by n intervals (DAY / MONTH / QUARTER / YEAR) CALCULATE([Total Sales], DATEADD(DimDate[FullDateAlternateKey], -1, MONTH))
Composing a YoY % measure
Time intelligence functions are almost always chained: build the comparison period first, then divide. Same formula as the payoff on CALCULATE, FILTER & Modeling.
Sales LY = CALCULATE([Total Sales], SAMEPERIODLASTYEAR(DimDate[FullDateAlternateKey])) YoY Growth % = DIVIDE([Total Sales] - [Sales LY], [Sales LY])
07

Relationships & Lookups

These reach across the DimProduct↔FactInternetSales relationship built for Module 2's assignment — beyond this course's core four lesson pages, but still well inside the basic-to-CALCULATE-mastery ceiling, not expert territory.

RELATED(column)
Pulls a column from the "one" side of a relationship into a calculated column on the "many" side.
Product Line = RELATED(DimProduct[ProductLine]) // written on FactInternetSales, the "many" side
RELATEDTABLE(table)
The reverse direction — returns matching rows from the "many" side, seen from the "one" side.
Orders per Product = COUNTROWS(RELATEDTABLE(FactInternetSales)) // written on DimProduct, the "one" side
VALUES(column)
Distinct values of a column under the current filter context — the manual version of what SELECTEDVALUE (Context & Dynamic Measures) does in one call.
Selected Product Line = IF(
  HASONEVALUE(DimProduct[ProductLine]),
  VALUES(DimProduct[ProductLine]), "Multiple"
)
RELATED vs. LOOKUPVALUE
RELATED only works across an existing model relationship. Since DimProduct↔FactInternetSales already has one, RELATED is the better choice there — LOOKUPVALUE is for matching against a table with no relationship built at all.
Standard Cost (no relationship needed) = LOOKUPVALUE(
  DimProduct[StandardCost], DimProduct[ProductKey], FactInternetSales[ProductKey]
)

09

Common Pitfalls

Checklist before you submit a model

  1. Divide-by-zero. Never write a/b in a measure — use DIVIDE(a, b, 0), which returns a safe alternate value instead of an error.
  2. Columns bloat the model; measures don't. If a value only ever appears in a visual, make it a measure — calculated columns are stored per row and slow down large tables.
  3. Measures can't use bare row context. DimProduct[ListPrice] - DimProduct[StandardCost] fails inside a measure — wrap it in SUMX(DimProduct, ...) to give it a row to iterate over.
  4. CALCULATE filters replace, they don't add. CALCULATE(expr, DimProduct[ProductLine]="R") overwrites any existing filter on ProductLine rather than intersecting with it.
  5. Build measures on measures. Write [Total Sales] inside other formulas instead of repeating SUM(FactInternetSales[SalesAmount]) everywhere — one definition to fix later.
  6. Time intelligence needs a real date table. A column of dates isn't enough — mark a contiguous table as the official Date table (Model view → Mark as Date Table) before TOTALYTD or SAMEPERIODLASTYEAR will behave.
  7. FactInternetSales is one row per order LINE, not per order. AVERAGE(SalesAmount) quietly averages per line item, not per order — use DIVIDE([Total Sales], DISTINCTCOUNT(SalesOrderNumber)) for a true average order value.
