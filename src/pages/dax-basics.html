Calculated Column vs. Measure — the first fork in the road, and the single most-asked beginner question

Computed once per row, at data refresh, and physically stored in the table — like adding a new column in Excel with a formula dragged down every row.

Example: Full Name = [First Name] & " " & [Last Name] — one fixed value per row, doesn't change based on what's filtered on screen.

Computed at query time — the instant a visual asks for it — under whatever currently surrounds it.

Example: Total Sales = SUM(FactInternetSales[SalesAmount]) — the same measure returns a different number for "2025" than for "2024," automatically, with no formula change.

The rule of thumb: if the number should change when someone clicks a slicer, it's almost always a measure, not a calculated column. Answer this question on day one — nearly every early DAX mistake on this site's Troubleshooting page traces back to getting it backwards.

Implicit vs. explicit measures

Drag FactInternetSales[SalesAmount] straight into a Card's Values well and Power BI silently creates an for you — it sums by default, with no DAX written anywhere. It works, right up until it doesn't: implicit measures can't be reused across visuals by name, can't be reformatted once and have that stick everywhere, and don't show up cleanly in a Measures table for someone else to find. This course always writes explicit measures instead — Modeling ribbon → New Measure — for exactly those reasons.

The four formulas you'll reuse for the rest of this track

Same small set of measures, reused deliberately through every level that follows — watch [Total Sales] reappear inside [Sales YTD], then inside [YoY Growth %], rather than meeting 40 unrelated functions.

Total Sales = SUM ( FactInternetSales[SalesAmount] ) Total Quantity = SUM ( FactInternetSales[OrderQuantity] ) Order Count = DISTINCTCOUNT ( FactInternetSales[SalesOrderNumber] ) Average Order Value = DIVIDE ( [Total Sales], [Order Count] )
Why DIVIDE, never /: a plain / throws a hard divide-by-zero error the instant any row in context has a zero denominator — one empty slicer selection and the whole visual breaks. DIVIDE(numerator, denominator) returns blank instead (or a value you specify as a third argument) — a habit worth installing on your very first ratio, before the bad habit of reaching for / ever forms.

Also worth the aggregation family beyond SUM: AVERAGE, MIN, MAX, COUNT (counts non-blank values in a column), and COUNTROWS (counts rows in a table, no column needed) — all one-line, all filter-context-aware exactly like SUM.

Naming, formatting, and a home for your measures

  • ✓
    Business-readable names. Average Order Value, never Measure 1 or AOV_calc2 — a name a stakeholder can read on a tooltip without translation.
  • ✓
    Format every measure once. Currency, thousands separators, percentage — set in the Modeling ribbon the moment a measure is created. An unformatted 0.183947 where a viewer expects "18.4%" reads as unfinished, even when the math is right.
  • ✓
    One dedicated measures table. Create an empty table (Enter Data, no columns) named something like _Measures and keep every measure there instead of scattered across whichever table felt convenient — one obvious place to look, every time.

Iterators and row context — when summing a column isn't enough

Some numbers can't come from aggregating a column that already exists — they have to be computed row by row, then aggregated. That's an , and "row by row" is the first real meeting with — formalized further on Context & Dynamic Measures, but it starts here.

Total Margin = SUMX ( FactInternetSales, FactInternetSales[SalesAmount] - FactInternetSales[TotalProductCost] ) Margin % = DIVIDE ( [Total Margin], [Total Sales] )

SUMX walks FactInternetSales one row at a time, computes SalesAmount − TotalProductCost fresh on each row, and only then adds all those per-row results together.

Why not just SUM(SalesAmount) − SUM(TotalProductCost)? For a straight total, that actually gives the same answer — subtraction distributes over a sum either way. It stops working the moment the question changes shape: average margin per order needs each order's margin computed first, then averaged — AVERAGE(SalesAmount) − AVERAGE(TotalProductCost) silently produces a different, wrong number, because averaging first and subtracting first are not the same arithmetic. An iterator is required precisely when the calculation itself, not just the final aggregation, has to happen per row.

Close the loop from the top of this page: Total Margin and Margin % are exactly the kind of thing a student is tempted to build as a calculated column ("just add a Margin column to the table"). Don't — a calculated-column Margin can't respond to a Region slicer or a Date filter the way SUMX-built [Total Margin] does. If it should change when someone clicks something, it's a measure, full stop, even when the formula reaches into row context to get there.
