Joins combine tables. Relationships connect them.

Real analysis almost never lives in one table. There are two ways to bring tables together in Power BI: merge them into one table in Power Query, or keep them separate and relate them in the data model. This page covers both, with row counts you can check yourself, and ends with the star schema that AdventureWorksDW has used under every lesson so far.

Files for this page: PQ_Practice_Orders.csv (35 rows), PQ_Practice_Orders_Feb.csv (15 rows), PQ_Practice_Returns.csv (10 rows). You met them in the Merge and Append lessons. Load all three with Transform Data and name the queries Orders, Orders_Feb and Returns. Part 2 also uses AdventureWorksDW.

Merge or relate? Decide first

Merge (Power Query)Relationship (Model view)
What happensColumns from table B are physically copied into table A. One table comes outBoth tables stay as they are, and a line between them lets filters flow from one to the other
Best forLookups that belong on the row: return reason on an order, category name on a product (a dimension-to-dimension lookup)A fact table to its dimensions: orders to products, sales to dates, sales to customers
CostRepeats B's values on every matching row of A, so a big table gets biggerNothing is copied. The dimension is stored once
Rule of thumbIf it's 1:1 or it's a dimension borrowing from another dimension, merge. If a dimension describes many fact rows (1:many), relate.

Part 1 · Joins in Power Query

Append adds rows. Merge adds columns.

Append Home → Append Queries

Stacks tables with the same columns on top of each other. Orders (35) + Orders_Feb (15) = 50 rows, same 14 columns. Columns are matched by name, not position: a column called Qty in one file and Quantity in the other becomes two half-empty columns. Rename first.

Merge Home → Merge Queries

A matches rows on a key column (here Order ID) and brings in the other table's columns. The row count depends on the join kind, and choosing it is the whole skill.

The six join kinds, with real row counts

Join kindRowsThe business question it answers
Left Outer (the default)35"Show every order, with return details where there are any." 8 rows get a reason, 27 get null
Inner8"Only the orders that came back." Good for refund analysis
Left Anti27"Orders that were never returned." Worked on the M Language page
Right Outer10"Every return, with order details where they exist"
Right Anti2"Returns we can't match to any order." A data-quality alarm, worked below
Full Outer37"Everything from both sides." 35 orders + the 2 unmatched returns

Why 35 and not 34? Orders still contains the duplicated ORD2012 row. A join keeps whatever rows you give it, duplicates included, so clean before you merge.

Worked example: a Right Anti join as a data-quality check

Question: does every return have an order behind it? Refunds with no order are an audit problem, so a model shouldn't hide them.

Select Returns→Home → Merge Queries → Merge Queries as New→Top: Orders · Order ID→Bottom: Returns · Order ID→Join Kind: Right Anti

Result: 2 rows, ORD2036 (Defective, ₹899) and ORD2044 (Wrong item shipped, ₹299). The Merge dialog's match count at the bottom hints at it before you click OK: only 8 of the 10 returns find a match.

The two orders aren't missing. They're in Orders_Feb. The Returns export covers both months, but we only joined it to one. The fix is to combine the order files first:

  1. Select Orders → Home → Append Queries as New → Table 2: Orders_Feb. Rename the result AllOrders: 50 rows
  2. With AllOrders selected, Ctrl+A on the headers → right-click → Remove Duplicates: 49 rows (ORD2012 collapses to one)
  3. Right-click Orders and Orders_Feb → uncheck Enable load. They're now staging queries feeding AllOrders
  4. Repeat the Right Anti merge with AllOrders on top: 0 rows. Every return is accounted for
  5. Now merge for real: AllOrders → Merge Queries → Returns on Order ID → Left Outer. The footer reads "matches 10 of 49 rows from the first table"
A habit worth keeping: before any Left Outer merge, run the Right Anti version once. If it returns anything, your "lookup" table has rows your main table doesn't know about, and a Left Outer join would drop them without a word.

Expanding the merged column

A merge doesn't bring columns in straight away. It adds one column, named after the other query, whose cells say Table: each one holds the matching rows from Returns. Click the ⇄ expand icon in its header:

  • Expand: tick Return Reason and Refund Amount. Leave Order ID unticked, since you already have it
  • Untick Use original column name as prefix, or you get Returns.Return Reason
  • Aggregate (the other radio button) returns one summary per row instead of every match, e.g. Sum of Refund Amount. Use it when one order can have several returns and you want one row per order

Four ways a merge goes quietly wrong

ProblemWhat you seeFix
Duplicate keys on the lookup sideMore rows after expanding than before. Example below: 49 orders become 59Make the lookup key unique first (clean, then Remove Duplicates on the key). Check the row count before and after every merge
Keys that look equal but aren'tFewer matches than expected. Matching is exact: "ORD2003 " ≠ "ORD2003", and "ord2003" ≠ "ORD2003"Trim and fix case on both key columns before merging. Fuzzy matching (a Merge dialog option) exists for names, never for IDs
Different typesZero matches: the text "2001" never equals the number 2001Set both key columns to the same type
Composite keysA single column isn't unique (e.g. an order number repeats per line)Ctrl-click several key columns, in the same order on both sides. The dialog numbers them 1, 2…

The 49 → 59 example, for real: build a Products lookup by removing duplicates across Product Code + Category without cleaning Category first, and SKU-1004-BLK appears twice (once as "Electronics", once as "electronics", from ORD2009). Merge it into AllOrders and each of that product's 10 orders matches twice: 49 rows become 59, and revenue for that product doubles. Part 2 builds this table properly.

Part 2 · Data modelling

Once tables are loaded, the Model view (third icon on the left edge of Power BI Desktop) shows them as boxes, with relationships as lines. A model that's well shaped makes DAX short and correct. A badly shaped one makes every measure a workaround.

Facts, dimensions, and the star schema

Fact table

One row per event: a sale, an order line, a return. Mostly numbers you'll add up (SalesAmount, OrderQuantity) plus keys pointing at dimensions. Long, and it keeps growing. See .

Dimension table

One row per thing: a product, a customer, a date. Descriptive text you'll slice by (Color, City, CalendarYear) and a unique key. Short and wide. See .

Know your grain. The grain of a fact table is what one row means. FactInternetSales is one row per order line (SalesOrderNumber + SalesOrderLineNumber), not per order. That's why COUNTROWS counts lines and DISTINCTCOUNT(SalesOrderNumber) counts orders, the "average that lies" from DAX Practice. Write the grain down before you write a single measure.

Build a star from the practice files

AllOrders mixes two kinds of information: facts about each order, and facts about each product (Category repeats on every order of that product). Splitting the product information out into a proper dimension:

  1. Right-click AllOrders → Reference. Rename the new query Products
  2. Home → Choose Columns → keep only Product Code and Category
  3. Select Category → Transform → Format → Capitalize Each Word. This must come before the next step, or "electronics" survives as a separate row
  4. Select Product Code → right-click → Remove Duplicates: 5 rows, one per SKU. Column distribution should read 5 distinct, 5 unique
  5. Back in AllOrders, remove the Category column. It now lives in Products, the one place it's defined
  6. Close & Apply → Model view → drag Products[Product Code] onto AllOrders[Product Code]

Power BI detects Many to one (*:1), cross-filter Single: many order rows per product, and filters flowing from Products to AllOrders. A bar chart of order count by Products[Category] now shows exactly 4 bars, with no stray "electronics".

If you skipped step 3: Products has 6 rows and SKU-1004-BLK isn't unique. Power BI can't make it the "1" side, so it proposes Many to many with a warning. In a beginner model, a many-to-many relationship you didn't plan almost always means a dimension key isn't unique. Go back and fix the data, not the relationship.

Relationship settings, decoded

Double-click any relationship line in Model view:

SettingOptionsWhat to pick
Many to one (*:1) · One to one (1:1) · Many to many (*:*)*:1, from fact to dimension, nearly always. 1:1 usually means the two tables should be merged into one. *:* means stop and check your keys
Cross filter directionSingle · BothSingle (dimension filters fact). Both can create ambiguous filter paths and slow reports. Use it only when you can say exactly why
Make this relationship activeOn · Off (dashed line)Only one active path may exist between two tables. The others stay inactive until a measure activates them

Which way do filters flow?

Filters travel along the relationship arrow, from the "1" side to the "*" side. Pick Color = Red in a slicer on DimProduct, and FactInternetSales narrows to red products' lines, so every measure on it responds. The reverse is where students get stuck:

"I picked a customer, but my product slicer still lists every product." DimCustomer filters FactInternetSales (1 → *). The filter doesn't continue backwards from the fact up into DimProduct with Single direction, so the product list isn't narrowed. The measures are still correct; only the slicer's list isn't filtered. The fix is not to switch to Both. Put a measure on the product slicer as a visual-level filter (Total Sales is not blank), so only products this customer actually bought are listed.

Three dates, one active: role-playing dimensions

FactInternetSales has three date keys: OrderDateKey, DueDateKey and ShipDateKey. Importing from AdventureWorksDW creates a relationship from each to DimDate, but only one can be active (solid line). The other two are dashed. Every time-intelligence measure in Module 3 assumes the active one is OrderDateKey, so check it:

  1. Model view → hover over each DimDate–FactInternetSales line to see which columns it joins
  2. If the solid line isn't OrderDateKey: double-click the active one → untick Make this relationship active → OK. Then double-click the OrderDateKey line → tick it → OK

Analysing by ship date instead needs CALCULATE([Total Sales], USERELATIONSHIP(FactInternetSales[ShipDateKey], DimDate[DateKey])). That's past this course's DAX ceiling. It's here so you recognise the dashed lines, not so you use them yet.

Snowflakes: flatten them with a merge

Product category is two hops from the fact: DimProduct → DimProductSubcategory → DimProductCategory. Relating all three works, but the Fields pane then shows three product tables. This is the dimension-to-dimension case where a merge is the right tool:

  1. In Power Query, select DimProduct → Merge Queries → DimProductSubcategory on ProductSubcategoryKey → Left Outer
  2. Expand → tick EnglishProductSubcategoryName and ProductCategoryKey
  3. Merge again → DimProductCategory on ProductCategoryKey → Left Outer → expand EnglishProductCategoryName
  4. Uncheck Enable load on DimProductSubcategory and DimProductCategory. They were only needed for the lookup
Why Left Outer, not Inner: some AdventureWorksDW products (mostly components that are never sold online) have no subcategory. An Inner join would silently delete them from DimProduct. Any sale of such a product would then show up under a (Blank) product in every visual.

The (Blank) row: when a key has nowhere to go

If a fact row's key has no match in its dimension (a sale for product 999 that isn't in DimProduct), Power BI still counts the sale but groups it under a (Blank) item in every slicer and axis built from that dimension. It's the model's version of the Right Anti check from Part 1. Find the orphan keys with a Left Anti merge, fact on top and dimension below, then fix the dimension or the source data.

Model checklist

  1. Each fact table has a stated grain, and each dimension has a key that's genuinely unique (column distribution: distinct = unique = rows)
  2. Relationships run *:1, Single, dimension → fact. Any 1:1, *:* or Both has a reason you can say out loud
  3. A marked date table (DimDate) with the order date as the active relationship
  4. Snowflakes flattened into their parent dimension where it simplifies the Fields pane
  5. Key columns on the fact side hidden (right-click → Hide in report view). Slicers should use the dimension's column, never the fact's copy of the key
  6. No unplanned (Blank) items in any slicer

Take-away exercise

Download Sales_Clean.csv. Build a SubCategories dimension from it with Reference → Choose Columns (Sub Category, Category) → Remove Duplicates on Sub Category. You should get 25 rows across 5 categories. Remove Category from the Sales query, relate the two tables *:1 on Sub Category, and build a Matrix of Sales by SubCategories[Category] → Sub Category.

Remove Duplicates on Store leaves 12 rows, but open the column profile first: "UrbanMart Store 01" appears with 6 different cities. What does that tell you about whether Store is really a key in this file, and which city would your dimension keep?

Check yourself

A Left Outer merge of Orders (49 rows) with a lookup table returns 59 rows. What happened?

The lookup table has duplicate keys, so some orders matched more than one row. Every duplicate multiplies that order's rows, and its sales along with them. Make the lookup key unique (clean, then remove duplicates on the key) and re-merge. A Left Outer merge onto a unique key never changes the row count.

Returns has one row per order that was returned. Merge it into Orders, or relate it?

Merge. It's 1:1: at most one return per order, so its columns belong on the order row. A 1:1 relationship between two tables is usually a sign they should be one table.

Power BI suggests a Many-to-many relationship between Products and Orders. What do you check first?

Whether the Products key is really unique. Open its column distribution: if distinct ≠ unique, some product appears twice, usually because of an uncleaned descriptive column (like "Electronics" vs "electronics") that made two rows survive Remove Duplicates.

Why does a slicer on DimProduct filter FactInternetSales, but a slicer on DimCustomer doesn't shorten a product list?

Filters flow from the 1 side to the * side. Both dimensions filter the fact, but with Single direction nothing flows from the fact back up into another dimension. Measures are still correct. To shorten the list, filter the product visual by a measure (e.g. Total Sales is not blank) instead of switching the relationship to Both.
