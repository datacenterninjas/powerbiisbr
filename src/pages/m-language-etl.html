Every click in Power Query is secretly writing code

M is the language behind every transformation on the Power Query page — you've already been generating it by clicking buttons. This page opens that hood, then uses it to build one continuous Extract → Transform → Load pipeline on a single messy file, start to finish.

Joins, properly named

The Power Query page's "Merge Queries" lesson already teaches a Left Outer join — attaching Returns data onto every Order, keeping every order whether it was returned or not. That's ONE of several join types Power Query supports under the same Merge dialog:

Join kindKeeps
Left Outer already taughtEvery row from the first table, matched rows from the second
Right OuterEvery row from the second table, matched rows from the first
Full OuterEvery row from both tables, matched or not
InnerOnly rows that match in both tables
Anti (Left/Right)Only the rows that DON'T match — e.g. "orders with no return on file"

One worked Anti join, using the same two files as the Merge Queries lesson — PQ_Practice_Orders.csv and PQ_Practice_Returns.csv — but asking the opposite question this time: not "which orders have return info," but "which orders were NEVER returned at all."

Home → Merge Queries→First table: Orders, matching column Order ID→Second table: Returns, matching column Order ID→Join Kind: Left Anti→OK

No expand step needed this time — a Left Anti join doesn't bring in any columns from the second table, because its entire job is different: it keeps only the Orders rows that found zero match in Returns, and drops everything else. The result answers "which orders were clean, start to finish" directly, as a row count, with no further filtering required.

Common mix-up: a Left Anti join is NOT "Left Outer, then filter out the matched rows afterward" — though that would give the same final answer, Anti does it as one join step instead of two, which is both faster and leaves a cleaner Applied Steps pane for someone else to read later.

Steps 1–5: standardize text, the UI way

Everything in this block is already familiar from the Power Query page — no new M needed yet.

  1. Select Restaurant → Transform → Format → Trim, then Format → Capitalize Each Word — collapses all 10 "Punjabi Dhaba" rows to one spelling
  2. Select Cuisine → Transform → Format → Trim — fixes row 11
  3. Right-click City → Replace Values → "bengaluru" → "Bengaluru", then again → "Bangalore" → "Bengaluru", then again → "MUMBAI" → "Mumbai"
  4. Right-click Payment Mode → Replace Values → "Cash on Delivery" → "COD", then Transform → Format → Uppercase to catch "upi" and "cod" in one pass
  5. Right-click Rating → Replace Values → "Not Rated" → leave Replace With blank (null) — now every non-answer is a genuine null, not a mix of blanks and text
Order matters on step 3: replacing "Bangalore" → "Bengaluru" has to happen as its own explicit rule — Capitalize Each Word or a simple case-fix would never catch it, because "Bangalore" isn't a casing problem, it's a completely different word for the same place.

Step 6: Order Value — text-to-number, one column at a time

  1. Right-click Order Value → Replace Values → Value To Find: ₹ → Replace With: (blank)
  2. Right-click Order Value again → Replace Values → Value To Find: , → Replace With: (blank)
  3. Click the column's type icon → Whole Number

Row 40's -200 converts cleanly — it's a valid whole number, just an implausible one. Leave it as-is for now and flag it in a review note, the same judgment call the DAX Practice page's Tier A problems make about implausible-but-valid data: not a mechanical fix, a business one.

Step 7: Delivery Time — your first hand-written M column

The UI can Extract text before/after a delimiter, or Remove Errors after a type change — but neither one cleanly says "strip ' mins' if it's there, treat 'N/A' as nothing, then try converting to a number, all in one step." That's exactly the kind of small, specific logic a custom column earns its keep for.

Add Column→Custom Column→Column Name: Delivery Time (Clean)
= let raw = [Delivery Time], stripped = Text.Trim(Text.Replace(raw, " mins", "")), asNumber = try Number.FromText(stripped) otherwise null in asNumber

Text.Replace only changes the text if " mins" is actually present — safe to run on every row, not just row 10. try ... otherwise null is M's error-handling pattern: attempt the number conversion, and if it fails (row 37's "N/A", row 24's blank), return null instead of letting the whole column error out. Delete the original Delivery Time column and rename this one in its place once you've checked the result.

Step 8: Order Date — the flagship lesson, a hand-written M function

This is the one problem on this page the point-and-click UI genuinely cannot solve. Power Query's automatic date type detection applies one format to the entire column — it can fix a column that's consistently DD-MM-YYYY, but Order Date has three different formats mixed together, and no single Change Type click can read all three correctly at once.

Why this matters more than it looks: if you just click the type icon and choose Date here, Power Query guesses based on the first few rows, silently misreads every row that doesn't match, and throws no error you'd ever see — the exact "Line Chart is quietly wrong for months, nothing on screen tells you" trap from the Power Query page's date lessons, at full strength.
  1. Home → New Source → Blank Query (this becomes a reusable function, not a table)
  2. View → Advanced Editor, delete the default content, paste the function below, click Done
  3. Rename the query fnParseOrderDate in the Queries pane
let ParseOrderDate = (dateText as text) as nullable date => try if Text.Contains(dateText, "/") and Text.StartsWith(dateText, "20") then Date.FromText(dateText, [Format = "yyyy/MM/dd"]) else if Text.Contains(dateText, "/") then Date.FromText(dateText, [Format = "dd/MM/yyyy"]) else Date.FromText(dateText, [Format = "dd-MM-yyyy"]) otherwise null in ParseOrderDate

Read it top to bottom: if the text contains a slash AND starts with "20" (a year), it's row 16's shape — yyyy/MM/dd. If it contains a slash but doesn't start with a year, it's row 30's shape — dd/MM/yyyy. Otherwise it's the standard dd-MM-yyyy shape every other row already uses. The whole thing is wrapped in try ... otherwise null — row 43's "31-02-2025" matches the standard-format branch syntactically, Date.FromText then fails to construct it because February 31st isn't a real date, and the outer try catches that failure and returns null instead of crashing the query.

  1. Back in the FoodDelivery query, Add Column → Custom Column → Column Name: Order Date (Clean)
  2. Formula: = fnParseOrderDate([Order Date])
  3. Check the column's type icon reads Date automatically (the function's as nullable date return type tells Power Query what it is) — set it explicitly if not
  4. Delete the original Order Date column, rename this one in its place
What just happened, in plain terms: a hand-written function is nothing more than logic you couldn't express as a single button click, given a name, and reused with one line — fnParseOrderDate([Order Date]) reads almost like plain English once it exists, even though what's happening underneath (three conditional parse attempts wrapped in error handling) would take five separate UI steps to approximate, badly.

Step 9: the housekeeping that's left

  1. Select all columns (Ctrl+A on the headers) → Right-click → Remove Duplicates — collapses row 65 into row 52
  2. Confirm Rating's type is Decimal Number (the blanks and former "Not Rated" nulls should pass through cleanly)
  3. Leave Order Status (Delivered / Cancelled / Refunded) as-is — don't filter it out here. The next page needs all three states: a Total Orders KPI counts everything, while a Revenue KPI needs to filter to Delivered only — that's a job for a DAX measure, not a Power Query step that would throw away information a different KPI still needs

Load

Right-click the query name→Rename to "FoodDelivery"→Home→Close & Apply

Scroll the Applied Steps pane top to bottom before applying — every fix above should be its own named step, in the order you built them. That list, read straight through, IS the ETL pipeline: Extract (the Source step), Transform (everything from Trim through the two custom columns), Load (Close & Apply writes it into the model as the table FoodDelivery).
