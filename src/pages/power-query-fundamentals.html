Power Query is a recipe, not an edit

Before the 25 hands-on lessons on the next page, this page gives you the mental model underneath them: where Power Query sits in Power BI, what the editor's panes are for, why your source files are never touched, and the habits that decide whether a query still works next month. Everything here uses PQ_Practice_Orders.csv, the same file the next page's lessons use.

What Power Query is for (and what it isn't)

Power Query · M

Shapes the data

Works on rows and columns before they're loaded. It fixes typos, sets types, removes duplicates, splits and merges columns, stacks monthly files, joins tables and reshapes wide data into long data. Its output is a clean table.

DAX

Calculates on the data

Works on the loaded model, responding to whatever a viewer has filtered. It produces % of total, YoY growth, running totals and anything else whose answer depends on the slicer. Its output is a number in a visual. See Module 3.

The jobToolWhy
"online", "ONLINE" and "Onlin" should all read "Online"Power QueryFixing a value is shaping, and it should happen once, at the source, for every report built on it
Remove the duplicated ORD2012 rowPower QueryOnce duplicates are loaded, every measure is quietly wrong
Stack January's and February's order filesPower QueryAppend is a Power Query operation, and there's no clean DAX equivalent
A "Line Total" per row = Qty × Unit PricePower Query (custom column)It's a fixed per-row value. A DAX calculated column also works, but it's computed after load and bloats the model the same way
Each channel's % of total revenueDAXThe answer changes with every slicer, so it has to be calculated at query time
Revenue this year vs. last yearDAXTime intelligence works against the model's date table, not the raw file
The rule of thumb practitioners use: transform data as far upstream as possible, and as far downstream as necessary. If it can be fixed in the source system, fix it there. Otherwise fix it in Power Query. Leave to DAX only what has to respond to the viewer.

Transform tab vs. Add Column tab: the same buttons, different results

Many buttons appear on both tabs: Extract, Format, Parse, Date and Standard math. They differ in what happens to the original column:

Transform → Extract → First Characters (8)

Product Code changes in place: SKU-1001-RED becomes SKU-1001. The color suffix is gone from this query.

Add Column → Extract → First Characters (8)

Product Code stays as it was, and a new column First Characters holds SKU-1001. Nothing is lost.

Unsure which one you want? Use Add Column. You can always delete the original column later, but you can't get it back from a transformed column without undoing the step.

Applied Steps: the recipe that replays on every refresh

Nothing you do in Power Query edits the CSV. Each click adds a step to the query's recipe, and each step takes the previous step's table as input and outputs a new one. On every refresh Power BI re-reads the source and replays every step, top to bottom. That's why you do the cleaning once: next month's export gets the same treatment automatically.

Click an earlier step

The preview shows the data as it was at that step. It's the fastest way to find where a problem came from.

Click a step's gear ⚙

Reopens that step's dialog with its settings, so you can change a Replace Values without redoing it.

Right-click → Rename

"Replaced Value3" tells a teammate nothing. "Fix Onlin typo" does. Right-click → Properties also lets you add a description.

The #1 way queries break: steps refer to columns by name. Rename Qty to Quantity in step 4, and a step 7 that still says "Qty" fails with Expression.Error: The column 'Qty' of the table wasn't found. Deleting or reordering a middle step causes the same failure. Power Query warns you when you insert a step mid-recipe for exactly this reason. After any change in the middle, click the last step and check it still works.

Try it: watch the recipe build

  1. Open PQ_Practice_Orders.csv with Transform Data. Two steps already exist, Source and Promoted Headers, and usually a third, Changed Type, which Power Query adds on its own
  2. Select First Name → Transform → Format → Trim. A Trimmed Text step appears. "Rohit " (ORD2002) and " Swati" (ORD2007) lose their stray spaces
  3. Select Channel → Transform → Format → Capitalize Each Word. Now click back on the Trimmed Text step: the lowercase online values are still there, because that step comes before the fix
  4. Click the last step again, then right-click it → Rename → Proper-case Channel
  5. Open View → Advanced Editor. Each step you clicked is one line of M code. The M Query page teaches you to read and write these lines

Data types first, and the locale trap

Every column has a type, shown by the icon in its header: ABC text, 123 whole number, 1.2 decimal, a calendar for date, ABC/123 "any" (untyped, which is always a to-do). The automatic Changed Type step guesses types from the first rows. Treat that guess as a draft, not as settled.

Dates are where the guess goes wrong. PQ_Practice_Orders.csv writes dates as DD-MM-YYYY: 03-01-2025 is 3 January. Power Query parses dates using your computer's regional setting. If that setting is US English (MM-DD-YYYY), this is what happens to the file's 35 rows:

RowsExampleResult under US English
1203-01-2025 (ORD2001)Silently wrong: becomes 1 March. The day is ≤ 12, so it's a valid US date. No error, no warning
2022-01-2025 (ORD2012)Error: there's no 22nd month
32025/01/09, 2025-01-15, 25/01/2025Different formats entirely (ORD2004, ORD2008, ORD2014). One locale can't fix these
Right-click Order Date→Change Type→Using Locale…→Data Type: Date · Locale: English (India)

With the locale set, the 32 DD-MM-YYYY rows parse correctly regardless of whose computer refreshes the file. The 3 odd-format rows need the hand-written M function on the M Language & End-to-End ETL page.

The dangerous rows are the 12, not the 20. Errors are visible. A date that became 1 March instead of 3 January is a correct-looking date. Your month-over-month chart is now wrong, and nothing on screen says so.

Column profiling: check the data, don't assume it

Turn on all three in the View ribbon: Column quality, Column distribution, Column profile. Then click the status bar text "Column profiling based on top 1000 rows" and switch to entire data set. On a large file, a problem in row 1,001 is invisible otherwise.

IndicatorWhat it tells youOn PQ_Practice_Orders.csv
Column quality% Valid / Error / EmptyOnce Qty is typed as a whole number: 1 Error (N/A, ORD2011) and 1 Empty (ORD2006)
Column distributionDistinct = how many different values · Unique = values that appear exactly onceChannel: 7 distinct, 4 unique, but there are only 2 real channels. Power Query compares text case-sensitively, so Online, online, ONLINE and Onlin all count separately

A key column like Order ID should show distinct = unique = row count. Here it shows 34 distinct, 33 unique, 35 rows: that's the duplicated ORD2012, found without scrolling.

Managing queries: Duplicate, Reference, and staging

DuplicateReference
What you getA full copy of every step, independent from then onA new query whose single first step is "start from the other query's result"
Fix a bug upstreamYou fix it twice, or forget the copyFixed everywhere at once
Use it forExperimenting without risking the originalBuilding several tables from one cleaned source, e.g. a Products dimension from the Orders query (see Joins & Data Modelling)
  • Enable load: right-click a query → uncheck Enable load for intermediate "staging" queries that exist only to feed another query. Its name turns italic and it never becomes a model table. That keeps the Fields pane clean and the file smaller.
  • Name queries like tables: the query name is the model table's name. Orders, not PQ_Practice_Orders (2).
  • Group them: right-click → Move To Group → New Group, e.g. Staging, Dimensions, Facts.
  • Close & Apply loads and closes, Apply loads and stays open, Close keeps pending changes unapplied (Power BI shows a yellow banner until you apply them).

Query folding: letting the database do the work

When the source is a database such as AdventureWorksDW on SQL Server, Power Query tries to your steps: translate them into one SQL query the server runs, so only the finished result travels over the network. Filtering FactInternetSales to one year, removing 20 unused columns, and grouping by product can all become a single SELECT … WHERE … GROUP BY that returns a few hundred rows, instead of pulling 60,000 rows and filtering them on your laptop.

Right-click a step→View Native Query→enabled = this step folds · greyed out = it doesn't (or can't be shown)
usually folds

Remove/choose columns, filter rows, rename, sort, Group By, simple merges between tables in the same database, most type changes

usually breaks folding

Adding an Index column, most custom M functions, merging with a table from a different source (e.g. a CSV). Once one step stops folding, every step after it runs locally

Practical rule: put the steps that shrink the data (remove columns, filter rows) first, while folding still works. Flat files (CSV, Excel) never fold, because there's no database engine to hand the work to. That's fine for 35 rows, but it matters on a real warehouse.

A good step order

  1. Remove columns you don't need and filter rows you'll never report on, early (it also helps folding)
  2. Clean text (trim, fix case, replace typos) before setting number/date types, because "₹1,158" or "N/A" won't convert
  3. Set types deliberately, using a locale for dates. Delete an automatic Changed Type step if it guessed wrong, rather than stacking a second one on top
  4. Standardize, then remove duplicates. Online and online rows aren't duplicates to Power Query until they're spelled the same
  5. Merge and append last, once both sides are clean. A join on a dirty key silently misses matches
  6. Rename steps and queries, and turn off load for staging queries, before you hand the file to anyone

Check yourself

You fixed a typo in Power Query. Did the CSV file on your disk change?

No. Power Query never writes back to a source. The fix is a step in the query's recipe, replayed on every refresh. That's why it also applies to next month's file.

A query worked yesterday. Today, after you renamed a column in step 3, step 9 shows an error. What happened?

Step 9 still refers to the column by its old name. Steps reference columns by name, so a rename upstream breaks every later step that uses the old name. Click step 9's gear (or edit its formula) and use the new name.

Order Date converted to Date with no errors at all. Why might it still be wrong?

If the values are DD-MM-YYYY and your locale is MM-DD-YYYY, every date with a day ≤ 12 converts to a valid but wrong date. No errors doesn't mean correct. Convert with Change Type → Using Locale and spot-check a few dates you know.

You need an Orders table and a Products table built from the same cleaned file. Duplicate or Reference?

Reference. Both tables then start from the one cleaned query, so a cleaning fix made once reaches both. With Duplicate, you'd have two copies of the cleaning steps to keep in sync.
