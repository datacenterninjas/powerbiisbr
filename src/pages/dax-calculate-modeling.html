CALCULATE: the one function that changes everything else

CALCULATE is the function that lets a measure override its own filter context on purpose — arguably the single most important function in all of DAX.

Everything in Time Intelligence and Context & Dynamic Measures was preparation for one sentence: CALCULATE means "compute this measure, but under a filter context I specify." Four steps below, ending with a payoff — re-deriving a formula from two pages ago, now that you can actually read what it was doing.

Step 1 — A boolean filter: CALCULATE as a permanent slicer

Road Bike Sales = CALCULATE( [Total Sales], DimProduct[ProductLine] = "R" )

Read this as: "Compute [Total Sales], but first override the filter context so only ProductLine = "R" (Road) rows count — regardless of what the report's own slicers currently say." That override is the entire trick. The second argument acts like a slicer nobody can move, baked directly into the formula.

Common confusion: this looks like it should behave the same as putting a Filters-pane filter on the visual instead. It doesn't, quite — a visual-level filter can be seen and removed by anyone editing the report; a condition baked into CALCULATE travels with the measure everywhere it's used, on any visual, forever, until someone edits the DAX itself.

Step 2 — FILTER: when the condition needs an expression

A bare Column = "Value" only handles equality. The moment the condition needs comparison logic — greater than, a calculation, multiple conditions — CALCULATE needs a table expression instead, and FILTER is how you build one.

Premium Product Sales = CALCULATE( [Total Sales], FILTER( DimProduct, DimProduct[ListPrice] > 1000 ) )

FILTER(DimProduct, DimProduct[ListPrice] > 1000) walks DimProduct row by row (that's row context, from DAX Basics, showing up again) and keeps only the rows where the condition holds — CALCULATE then uses that shortened table as its filter, instead of a single column=value pair.

Step 3 — ALL: from narrowing to widening

Every example so far has made CALCULATE narrow the context further. ALL flips the direction entirely — it strips filters away instead of adding them, and that single flip unlocks the pattern MBA students reach for constantly: share of total.

All Product Sales = CALCULATE( [Total Sales], ALL( DimProduct ) ) % of All Products = DIVIDE( [Total Sales], [All Product Sales] )

On a Matrix broken out by ProductLine, [Total Sales] shows each line's own number, but [All Product Sales] shows the SAME grand total on every single row — because ALL(DimProduct) tells CALCULATE to ignore whatever ProductLine the row is filtered to and total every product instead. Divide the row-level number by that constant grand total and every row now shows its own share of 100%, correctly, with zero manual work.

Step 4 — ALLEXCEPT and ALLSELECTED, briefly

ALLEXCEPT

Removes every filter on a table EXCEPT the columns you name. CALCULATE([Total Sales], ALLEXCEPT(DimProduct, DimProduct[ProductLine])) — total ignoring Class and Style filters, but still respecting ProductLine. A shortcut for "remove almost everything."

ALLSELECTED

Removes filters from inside the visual, but keeps whatever the report VIEWER explicitly selected outside it (a slicer). Gives "% of what's currently shown," not "% of literally everything" — the right choice when a viewer has already narrowed the page on purpose.

The payoff: re-reading Sales LY

Back on Time Intelligence, this measure was introduced with a promise to explain it later:

Sales LY = CALCULATE( [Total Sales], SAMEPERIODLASTYEAR( DimDate[FullDateAlternateKey] ) )

Nothing new is happening here that Steps 1–3 didn't already cover: SAMEPERIODLASTYEAR(...) is just a specialized table expression — like FILTER, but purpose-built to mean "the same dates, one year back" — handed to CALCULATE exactly the way FILTER(DimProduct, ...) was in Step 2. Every time intelligence function on this site is CALCULATE wearing a costume.

Relationships and data modeling best practices

None of the above works without a correctly built between tables — the same Data Model concept from the Architecture page, revisited with the modeling discipline a real project needs.

, not a web

One central fact table, dimension tables branching off it — never dimension-to-dimension relationships if a fact table can sit between them instead.

matters

Relationships should run from the "many" side (a fact table, many rows per customer) to the "one" side (a dimension table, one row per customer) — get this backwards and totals silently multiply.
